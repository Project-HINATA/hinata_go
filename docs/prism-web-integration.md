# PRiSM native store experience

Flutter's PRiSM implementation lives in `lib/features/prism/`: page widgets at the feature root, API/location/native bridge clients in `services/`, and visit state in `providers/`. Tests mirror this under `test/features/prism/`. Shared app routing and localization remain in their existing app-wide directories. Types and internal method channels use `Prism` / `prism`; the iOS target and sources use `PrismClip`. The App Clip bundle identifier is `moe.neri.hinatago.prism`; native OAuth returns through `hinata-prism-auth`. Signing profiles and the server association file must use the same App Clip identifier.

HINATA Go (iOS/Android) and the App Clip implement the in-store experience natively. A device QR/NFC opens its store and device context, authenticates with MuNET or Passkey, verifies shop QQ membership, confirms billing when needed, and obtains the TTLock door code. Power, card and coin actions remain native. The player can review their balance, assets and visit history, redeem a code, preview checkout and leave from a focused native sheet. Account settings and merchant management remain on Web; there is no new store dashboard entry in HINATA Go.

The previous interpretation that all unified devices should redirect to Web was corrected on 2026-09-12. Current clients use device capabilities to render the native flow and do not use the legacy `webOnly` compatibility hint to redirect. Empty devices show no operation controls. Only an explicit HA `off` state gates card/coin use; unknown or failed HA reads allow use. Automatic coins hide the manual coin button. Card completion, including partial or uncertain coin delivery, uses the same expired-session screen. The server sends one coin only after successful card relay acceptance; physical game-read timing is not confirmed by that response.

The clients use `/api/v1` and `{data}` responses, with structured error codes. Flutter shares the authenticated native HTTP session through its existing method channel on both mobile platforms. iOS and App Clip use the same API/model implementation. Android MuNET authorization returns through the existing `hinata-prism-auth` scheme and exchanges a one-time code into its native cookie session; only the identity provider authorization uses a browser. The full app bundle ID and `/t/:shop/:device` link shape are preserved. Both native clients derive the API origin (scheme, host and port) from the incoming HTTPS URL, including session creation, authentication, device/visit actions, images and Web links. Native cookies and Flutter visit state are isolated by origin. Incoming URLs with user information or invalid device identifiers are rejected. OS link associations include `link.neri.moe` and `link-beta.neri.moe`; additional domains require the corresponding platform associations to launch the app.

Device and money operations persist operation IDs per origin/user/store. Uncertain device actions are not resent. Financial retries retain their original body and ID; changing location permissions does not create a new debit request. Cards retain one-use device tickets. Account switches clear the native visit display. QQ verification and power-on poll the existing endpoints. Each operation requests native location only when the corresponding check-in, machine or checkout policy requires it. Checkout failure never ends billing; closing an app or completing a card swipe never checks out. The checkout page remains accessible after card delivery, including uncertain delivery.

Native regression checks: `flutter test test/features/prism/prism_visit_test.dart` covers QQ → entry → door → checkout, nonbilling/unknown HA, auto-coin button hiding, account-scoped pending requests and failure/retry behavior. `test/native/run-prism-visit-check.sh` compiles the actual Swift models, API and App Clip view model against an isolated URLProtocol fixture; only provider authentication and location are stubbed. It checks the same flow, distinct money retry IDs after rejection, stable IDs after lost replies, and expired-session behavior after partial coin results. Standard checks are `dart format .`, `flutter analyze`, `flutter test`, the App Clip/Runner simulator builds and Android debug APK build.

For simulator inspection, Debug builds accept `PRISM_API_ORIGIN` only for loopback hosts and the App Clip accepts `PRISM_PREVIEW_DEVICE_URL` as an invocation URL. Use these with the synthetic PRiSM preview on port 8790; the real link shape is `https://<deployment>/t/:shop/:device`. Release builds ignore both variables. No production credentials or physical commands are used in fixture tests. Production OAuth, real NFC invocation and physical read/coin timing require device acceptance.

The App Clip follows the Web device layout. Flutter uses Material 3 independently: theme surface containers, a subtly elevated 3:2 shop banner card, 24-point page margins, 40-point hero-to-task spacing, native card ListTiles on neutral surfaces and filled/outlined actions with at least 48-point targets. Store and device names remain below the banner; missing or failed images leave the same text panel without a decorative icon or an empty image slot. Admission uses a checkbox on both native platforms. The top-right account name opens logout and, for billed shops, Bill, Redeem, History and Wallet. These open focused native sheets. The account menu remains available on the expired-session screen. There is no player shop/device list, spending page, continue-device link or automatic ticket renewal. The routed Flutter regression covers accessible targets, long-bill scrolling with a fixed checkout footer, small-screen keyboard use, QQ clipboard copying and native checkout/return navigation.

QQ binding generates its code automatically when required, polls for completion, and renews expired codes. It displays only “绑定 QQ”, “在 QQ 群中发送”, the command and expiration; Bot contact and membership explanations are omitted. Any configured device can request explicit billing admission without a door lock, using its unexpired ticket and consent. Doors additionally retrieve a temporary password and can retrieve a new password from the same page. Power progress stays inside the button; manual coin becomes disabled “已投币”, backed by the server's per-ticket atomic claim (migration 0019). Transport uncertainty expires the physical-operation UI without retrying.

Player admission rates list the enabled `entryPricing` plans, including applicable global caps. Active rules appear in priority order with weekday/date conditions, complete overnight periods, unit rates, grace and caps. Absolute date ranges are supplied in the plan's local time and labeled as continuous periods; no date picker or time-zone label is displayed.

All three clients keep 140 points/pixels of top spacing for device content, in addition to the platform safe area. The account menu stays at the top right (8 points/pixels below the safe area), independently of that content spacing. Typography and layout follow each platform rather than matching pixel sizes across clients. Flutter task headings use the regular 24-point `headlineSmall`; card rows use `titleLarge` / `bodyMedium` (22 / 14), with an 88-point minimum height and comfortable padding, and buttons inherit Material label typography. The approved shop information card retains its existing hierarchy. Task headings remain centered. Account sheets follow platform conventions: Swift uses an inline native navigation title; Flutter uses a left-aligned Material 3 `titleLarge`, a native close button and the native drag handle. On iOS 26 the account Menu uses the native glass button style and system Liquid Glass menu; older iOS versions use the native bordered capsule. Flutter uses a tonal account button opening a native Material bottom sheet with native text menu rows and a separated logout row; Web uses a translucent capsule and backdrop blur.

Admission pricing lists only rules effective on the current local date, resolved centrally by the billing timeline engine and deduplicated by rule ID while preserving their original overnight ranges, in rule-priority order, with weekdays, dates and complete overnight ranges. No date selector or time-zone label is shown. The API supplies absolute date ranges formatted in the plan time zone. Player task headings remain centered. App Clip sheets retain the default system presentation background and native inline navigation title. On iOS 26 and later, `Button(role: .close)` has a white-tinted native glass style and black xmark. Its 44-point circle and 18-point top/trailing inset share the 40-point sheet corner's center; setting both together avoids mismatching a fixed button inset with a system-dependent corner radius. Earlier systems use a toolbar xmark button. Checkout stays in a bottom safe-area inset outside the scrolling bill. Flutter keeps its total, checkout action and header outside the scrolling content, including long bills and keyboard resizing. Sheet dates follow the app locale; financial values use tabular figures. Redeem uses a native filled text field. All Flutter surfaces follow the active light/dark or Android dynamic color scheme, without simulated glass. Do not infer API use from glass highlights in a still image or replace the sheet background to force a particular appearance. Current simulator captures use iOS 26.3.1; the user's Apple Maps reference uses iOS 27, whose rendering has not been validated locally.

Redeem remains disabled until a non-empty code is entered, matching Web and App Clip.

Flutter design references: [M3 lists](https://m3.material.io/components/lists/guidelines), [menus](https://m3.material.io/components/menus/guidelines), [bottom sheets](https://m3.material.io/components/bottom-sheets/guidelines), [buttons](https://m3.material.io/components/buttons/guidelines), and [Flutter text styles](https://api.flutter.dev/flutter/material/TextTheme-class.html). Mobile menus may adapt to bottom sheets. A card tap here is a single action, not a persistent radio selection; it retains the existing immediate login behavior. Ordinary account choices use list rows instead of repeated tonal buttons. Component shape and text roles come from Material; visual parity with Swift/Web is not a requirement.

Swift player task headings use the Dynamic Type-aware `.title2` style rather than a fixed 32-point bold font. Web follows the same default visual hierarchy with 1.375rem regular task headings and its existing system font stack. The shop information card is unchanged.

Manual coin uses a primary theme-filled Material button. Its existing `coinUsed` state disables the same button after success; progress stays inside it and repeated coin requests remain blocked server-side.

Native clients prefer the unified `locationEnabled` policy and fall back to legacy flags. They collect fresh coordinates for enabled entry/device/checkout requests; the API requires being inside for venue operations and outside for checkout. Poor or missing fixes retain the active visit.

The post-card delay uses the iOS 15-compatible nanosecond sleep API; it remains three seconds. The close toolbar item also uses an iOS 15-compatible ViewBuilder condition.
