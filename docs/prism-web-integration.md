# PRiSM native store experience

The Flutter PRiSM module has been removed. Flutter no longer contains PRiSM pages, routes, API clients, native bridges, or localization. Types and internal method channels use `Prism` / `prism`; the App Clip target, product and display name use `PRiSM Link`; its source directory remains `ios/PrismClip`. The App Clip bundle identifier is `moe.neri.hinatago.prism`; native OAuth returns through `hinata-prism-auth`. Signing profiles and the server association file must use the same App Clip identifier.

HINATA Go (iOS/Android) and the App Clip implement the in-store experience natively. A device QR/NFC opens its store and device context, authenticates with MuNET or Passkey, verifies a platform identity when the shop requires it, confirms billing when needed, and obtains the TTLock door code. Power, card and coin actions remain native. The player can review their balance, assets and visit history, redeem a code, preview checkout and leave from a focused native sheet. Account settings and merchant management remain on Web; there is no new store dashboard entry in HINATA Go.

The previous interpretation that all unified devices should redirect to Web was corrected on 2026-09-12. Current clients use device capabilities to render the native flow and do not use the legacy `webOnly` compatibility hint to redirect. Empty devices show “当前设备没有可操作项”. Only an explicit HA `off` state gates card/coin use; unknown or failed HA reads allow use. Automatic coins hide the manual coin button. Card completion stays on the device screen with a brief success checkmark before another swipe; coin, power and door controls remain available. The server sends one coin only after successful card relay acceptance; physical game-read timing is not confirmed by that response.

The clients use `/api/v1` and `{data}` responses, with structured error codes. iOS and App Clip use the same API/model implementation. Android MuNET authorization returns through the existing `hinata-prism-auth` scheme and exchanges a one-time code into its native cookie session; only the identity provider authorization uses a browser. The full app bundle ID and `/t/:shop/:device` link shape are preserved. Both native clients derive the API origin (scheme, host and port) from the incoming HTTPS URL, including session creation, authentication, device/visit actions, images and Web links. iOS session cookies use the system persistent cookie store and follow the server’s host-only cookie scope and expiry; Flutter visit state is isolated by origin. API responses bypass URL caching. Incoming URLs with user information or invalid device identifiers are rejected. OS link associations include `link.neri.moe` and `link-beta.neri.moe`; additional domains require the corresponding platform associations to launch the app.

A second link shape, `/t/:shopCode` with no device segment, opens the shop surface instead of a machine session. `InvocationParser` treats the two shapes as unambiguous because the machine form has one extra path component; an invalid link clears the shop and fails as before. Shop mode loads only the shop and the signed-in player’s own state — no machine session, no ticket. Admission is deliberately absent: a scanned machine ticket selects the machine context; physical arrival is enforced by shop location policy, so a player who has not checked in is pointed at the machine instead. Apart from admission and machine control, the shop link offers everything a device link does.

The shop and machine links share `start(shopCode:publicId:)`, `MachineLoginView`, and a single `ClipShopHero` position in `ClipSessionPage`. Only the public resource and task area differ: a machine creates a session and loads cards; a shop loads public shop information and reads the signed-in player's summary and checkout preview together. Shop links never request machine cards or create a ticket. Both use the same sign-in buttons, account menu, platform identity binding view and binding polling, error presentation, and settlement receipt. Shop information remains above sign-in after logout; private account state is cleared. A fresh URL resets its data, while another delivery of the current URL refreshes in place and preserves the receipt.

The card shows the same cover and shop name, with the billing state on the line that carries a machine name. Its width comes from the page and its image height follows the original aspect ratio; it neither crops the image nor fits it to the remaining vertical space. Image caching is shared between the two entry paths. The card stays at the same view-tree position when the task area changes from loading to bill or receipt.

The shop page owns one vertical scroll view. `ClipBillContent` contains only the shared totals and timeline, without another scroll container or an appearance-triggered request. The existing machine account sheet supplies its own scrolling and loading around that same content. Shop bill reads belong to the view model's refresh, and summary/preview publish only after both reads complete. Missing membership and disabled billing are completed states, not indefinite loading. The shop checkout button uses the shared `ClipCheckoutButton` in the page's bottom safe area; bill content is inset 24 points from the phone edge, matching the account sheet. The shop menu omits only 账单 and retains 兑换, 记录, 钱包 and 退出登录. Admission remains on machine links.

The checkout control is drawn as a transparent bottom overlay with scrollable tail padding. It does not use `safeAreaInset`, which would add an opaque system-background strip behind the button.

Checkout is a timeline, including after settlement. `player/checkout/confirm` returns the final timeline and total. The shared checkout action shows an animated circled checkmark, honors Reduce Motion, prevents duplicate submission, then dismisses the account sheet and switches to the ticket-free shop page. `ClipSettlementPage` reuses `ClipBillContent`; there is no separate line-item receipt or dismiss-to-admission button.

When no session is active, shop refresh reads `player/checkout/latest` and keeps the most recent settled timeline with “结账成功”, including after restarting the app. Active admission supersedes the old receipt; only players without a receipt see the NFC/QR admission hint. Origin/user changes and logout clear private state. This requires the corresponding PRiSM backend and migration `0027_checkout_timelines.sql`; older records use saved historical amounts, while new checkouts persist the full timeline atomically.

## Live Activity and Dynamic Island

Expanded Dynamic Island and Lock Screen activities share a bill summary: the elapsed visit time, the amount, and the earlier of the next charge or rule-switch countdown, all minute-precise (no seconds anywhere). Simultaneous events use one combined label. Compact presentation pairs the running time on the left with the countdown on the right. The optional `bill` in `StoreVisitAttributes.ContentState` is backward compatible with existing activities; all amounts arrive as integer cents and dates as Unix seconds.

Because a single session can stack several billing plans on one timeline, the activity deliberately renders no plan or rate text — the only unambiguous aggregates are the time in store, the amount, the next instant the amount can change, and cap headroom. The server may add these optional keys to `bill`, all additive and ignored by older builds. `remainingToCapCents` is the headroom to the effective cap at push time, computed by the server: with a single stacked plan, `min(global remaining, the current rule's remaining)`; with several stacked plans, the global remaining only — omit the key entirely when no global cap exists, because per-plan caps have no common aggregate once their rule switches diverge. No validity horizon is sent: every boundary that changes the aggregates (rule switches, cap-window switches, rule-anchor rollovers, charge points) is a backend alarm that pushes fresh values, so each sent value only needs to hold until the next push — the same freshness contract as the amount itself. 0 renders a "本时段已封顶" notice (segment-scoped by design: a later switch may open a fresh cap window). `billable: false` while no stacked plan is billable ("非营业") pauses the amount display and repoints the countdown at "恢复计费". `bill.nextEvent` (optional) is the single next event on the session's alarm timeline, pre-merged by the backend — every alarm candidate (charge points, rule switches, cap-window switches, billable transitions) is a peer and the earliest one wins, so the countdown is exactly the backend's next recompute-and-push; coincident candidates with different meanings arrive as one entry with a combined label. `atUnix` carries the instant and `label` the backend-rendered text (empty or missing renders a generic "下一事件"). The typed slots `nextChargeAtUnix`/`nextRuleAtUnix` were removed from the contract; builds that predate the wrapped event simply stop showing a countdown once the backend stops sending them. The legacy `planLabel` field is still accepted but no longer rendered. Layout-wise the lock-screen and expanded headers are symmetric: the leading side shows a small 在场时间 label over the running time in store (frozen total duration after checkout) with the check-in clock time in small print, and the trailing side shows the amount label over the amount with the cap notice in small print ("本时段已封顶" when capped, otherwise "距封顶还差 ¥x"). The compact presentation pairs a state icon (blue clock while metered, orange credit card while awaiting payment, gray pause while paused, green checkmark once settled) with the amount, and the minimal bubble shows the state icon alone. The countdown line shows the event's relative time with its absolute clock time in small print, and the footer carries the shop name plus the state notice. Swift renders only; it never recomputes pricing rules.

The manager requests `/player/live-activity/bill` on initial creation or stale recovery. It does not poll the endpoint on every screen refresh. Backend Durable Object alarms and business events push authoritative updates; Swift does not duplicate pricing rules. `staleDate` hides an expired countdown until new server data arrives. Closed but unpaid visits display “待结账” with a stopped duration; payment ends the activity. Ended duration is static rather than a running timer. Verify model decoding and countdown selection with `sh test/native/run-prism-activity-check.sh`; compile both Live Activity extension targets and the App Clip.

The lock-screen banner and Dynamic Island are a native-minimal presentation: a green/grey status dot, the shop name, a rounded monospaced timer, and a 轻点查看账单 hint. The activity no longer pins a black background, so it follows the system material in both light and dark. Its strings ship in a String Catalog (`ios/LiveActivityShared/Localizable.xcstrings`, en + zh-Hans) built into both widget extensions.

Tapping the activity opens `https://<origin>/t/:shopCode` through `widgetURL`, which lands on the same device-free shop surface: the native PRiSM sheet when the app or App Clip handles the link, and the web bill page in Safari otherwise. Two constraints follow from that. The activity records the HTTPS origin it was started under (link.neri.moe, the beta host, or a debug origin) and attaches no `widgetURL` when that origin is not HTTPS, so a debug loopback build cannot emit a broken link. The origin field is optional so an activity left over from an earlier build still decodes after an upgrade. The App Clip is launched by the existing `/t/` link prefix; the web fallback needs no new association.

The original App Clip invocation may be replayed when the clip is reactivated, and a Live Activity `widgetURL` is a separate explicit URL open. Both can therefore arrive within one foreground activation, in either order, and the clip's stored invocation is not replaced by the newer link. Routing keeps the delivery source so an explicit navigation cannot be overridden later in the same activation by a replayed App Clip invocation. An App Clip invocation ranks below an explicit open, because it carries the URL the clip was originally opened with and so can be stale; a Live Activity tap that carries no URL of its own reuses the link its activity was started for and ranks the same as an explicit open. The ranking is per activation and only rises, and it resets when the scene reaches the background — not on `.inactive`, which an ordinary transition passes through — so the next activation accepts a fresh invocation again. A bare `/t/{shop}` link is a legitimate invocation in its own right and is never classified by its shape. The source is taken from the system callback rather than inferred from timing, so no delay or batching is involved.

A link equal to the one already on screen refreshes in place: rebuilding there used to clear the active session and discard a settlement receipt, and it sent a shop page back to the machine page. This is separate from the ranking above and still applies. The main app defers presenting its sheet until a window exists, because a tap can arrive before the hierarchy is on screen, and it handles a URL delivered as an open rather than as a user activity.

Reads repeat once after a transient connection failure. `machines/session/start` is included in that set because a cold launch regularly loses its first request while the radio is still coming up, and it only mints a ticket: a repeated attempt leaves an unused row that expires rather than a charge. Billing and device actions stay excluded so they are never sent twice.

Device and money operations persist operation IDs per origin/user/store. Uncertain device actions are not resent. Financial retries retain their original body and ID; changing location permissions does not create a new debit request. Card sends are repeatable within a ticket. Manual and automatic coin sends share the backend device cooldown; the ticket stays usable until timeout. Account switches clear the native visit display. Platform identity verification and power-on poll the existing endpoints. Each operation requests native location only when the corresponding check-in, machine or checkout policy requires it. Checkout failure never ends billing; closing an app or completing a card swipe never checks out. The checkout page remains accessible after card delivery, including uncertain delivery.

## API offsets and native time display

The backend keeps business calculations and storage in UTC and returns shop events as offset-bearing ISO timestamps, for example `2026-10-03T10:08:00+08:00`. `prismParsedDate` parses them without adding any manual offset. Player admission/checkout/history, bill events and expiry times use the phone's display time zone. Store hours and rates use the shop's IANA zone, including day-preview segments and projected weekdays/dates. Live Activity epoch timestamps already represent absolute instants; SwiftUI renders their clocks in the phone zone and their timers need no change.

The main App and App Clip share this fix. Bill events use `at` for both time and date; charge periods use actual `startedAt/endedAt`. Legacy `event.time/date` and `periodLabel` are accepted in models but no longer determine the displayed clock. Rail comparisons use parsed instants rather than ISO string order. Cross-midnight periods show dates, and repeated wall-clock times across a DST rollback include offsets; durations and amounts are unchanged.

Run `test/native/run-prism-time-check.sh` with Swift for offset parsing, China/Japan display, phone/store zone differences, midnight, DST rollback, stale labels and unchanged durations. The Foundation/model check supports Linux; the SwiftUI source still requires Xcode for full type checking and device/simulator acceptance.

## Native scan performance and PRiSM request budgets

The companion backend change is [PRiSM PR #5](https://github.com/nerimoe/PRiSM/pull/5). Native machine links remain `/t/:shop/:device` and POST `machines/session/start`; ticket strings are opaque and never decoded by the client. Both old tickets and the backend’s new five-minute AES-GCM `v1.` tickets use the existing response model. Web fallback uses `/m#ticket=…`, so the browser's static request and referrer do not carry the ticket.

The public machine/shop request and identity read overlap. Once public data arrives, the hero is shown in the existing loading-task surface while identity is pending; it never claims the player is signed out prematurely. The initial visit context reuses the identity just loaded, including when a cold connection outlives the one-second cache window. Card loading and visit context overlap. Device state uses `includePower=0`, and HA is read separately from `devices/session/power`; HA cannot delay the card/mahjong UI. Only explicit off blocks use, and server action preconditions still validate current power. Off observations refresh approximately every three seconds; unknown/error observations back off. On/unmanaged observations finish until a full refresh or action needs another read. Power tasks stop on background, invocation changes, expiry and device actions, and their failure cooldown survives foreground changes.

Mahjong/device gate polling reads only dynamic state. Shop metadata refreshes on full/foreground reads, gate changes or after thirty seconds, and player summary reads are kept out of the ordinary three-second loop. Shop binding polling uses GET `platform-binding`; completed binding triggers a fresh metadata/summary read. Checkout previews/latest receipts are not fetched by unchanged dynamic polling.

`PrismAPI` coalesces and caches successful shop GETs for thirty seconds, identity and player-summary GETs for one second. Cache instances are scoped to API origin/cookie session; successful mutations (except read-only checkout preview and ticket minting), new invocations, explicit full refresh and detected user/gate changes clear them. A detected account switch clears private cards, assets and receipts before loading that account’s cards; explicit HTTP rejection (including a Retry-After response) clears the saved operation payload, while unknown device results keep it. A canceled subscriber does not cancel another subscriber’s transport. Failures are removed and stale in-flight completion cannot overwrite a newer cache entry. Billing/device mutations are never automatically replayed; the existing one extra safe-read/session-mint attempt after a network error is retained.

Typed and JSON error paths both retain HTTP status, structured code and `Retry-After` seconds/date. Silent polling fails at 5/10/20/30/60-second base delays with ±15% jitter, capped at sixty seconds; Retry-After is a floor that may exceed sixty seconds. Foreground events and link replays cannot bypass the cooldown; an explicit user refresh/action requests fresh context. Successful reads reset the failure budget. Live Activity token registration remains bounded to three attempts and now honors the same server retry floor. Backend APNs delivery/retention changes need no duplicated native billing alarm.

`sh test/native/run-prism-scan-check.sh` checks opaque fallback, structured 503/Retry-After, request coalescing/cancellation/invalidation/origin isolation, hero before identity, cards before HA and dynamic polling request counts using production API/model/state-machine sources. Existing visit, time, activity and manager checks remain in `.github/workflows/native-checks.yml`; Flutter formatting/analysis also run there. This PR workflow has no release/signing/publishing steps. Real device authentication, NFC and APNs delivery still use the existing acceptance process.

The unsigned `test/native/scan-preview` simulator host compiles the production SwiftUI view with the same shared model/API and mocked OS/HTTP boundaries. Its UI tests hold /me or HA indefinitely and attach Chinese mobile screenshots to the `native-scan-preview` CI artifact. It uses only synthetic data and neither real NFC nor production requests.

The persistent-cookie regression starts its real loopback HTTP fixture and waits for its port before running Swift; CI selects Python 3.13 to avoid relying on a runner’s developer-tool Python. Binding uses the loopback IP without a reverse-DNS lookup.

### 余额不足提示

Web 与 Swift（主 App / App Clip 共用 API 层）按 `INSUFFICIENT_BALANCE` 错误码显示本地化提示：中文“余额不足，请充值后重试”，英文“Insufficient balance. Please top up and try again.”。内部诊断文本变化不影响提示；HTTP 状态与错误码保留，余额不足不视为会话失效。结账被拒绝后保留当前账单和计费状态，不自动重发结账；充值后可手动重试，并使用新的操作 ID。
